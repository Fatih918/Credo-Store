# Supabase database and application setup

## Scope

The project includes:
- PostgreSQL catalog tables, administrator profiles, audit history, RLS policies, RBAC helper functions, and approved catalog seed.
- Supabase browser and server SSR clients.
- Next.js 16 Proxy session refresh using Supabase Auth cookies and `auth.getClaims()`.
- Admin email/password login and logout.
- Server-side active-profile and role authorization for the protected admin area.
- Runtime validation for the public Supabase URL and publishable key.

Not yet implemented: administrator invitation/role-management UI, category/subcategory CRUD, audit-log UI, or database-backed storefront reads. The current storefront continues to use its TypeScript catalog.

## Prerequisites

- Node.js 22+ and npm.
- A Supabase project for hosted integration.
- Supabase CLI and Docker for local database validation.
- A copy of the repository.

## Application environment

Copy `env.local.example` to `.env.local` in the project root, then fill in the values from Supabase Dashboard > Project Settings > API:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_SUPABASE_PUBLISHABLE_KEY
```

For local Supabase, the URL may use `http://127.0.0.1:54321`.

Only the project URL and publishable key belong in these public variables. Never place a secret key or legacy service-role key in a `NEXT_PUBLIC_*` variable. Keep `.env.local` out of Git.

The public storefront can still build and run without Supabase credentials. The Proxy skips session refresh when both public variables are absent. Supabase client creation fails with a clear configuration error if called before the variables are set. The admin login page displays a configuration notice until the public variables are provided.

## Local database validation

```bash
supabase start
supabase db reset
```

`supabase db reset` applies migrations to the local Supabase database from a clean state. Inspect the resulting tables and RLS policies before applying to a hosted project.

Useful checks in the Supabase SQL editor:

```sql
select c.name as category, s.name as item, s.pricing_type,
       s.promo_price, s.original_price, s.bonus_quantity
from public.categories c
join public.subcategories s on s.category_id = c.id
order by c.sort_order, s.sort_order;

select count(*) as category_count from public.categories;
select count(*) as subcategory_count from public.subcategories;
```

Expected seed counts: 3 categories and 15 subcategories.

## Hosted project

Link the CLI to the intended Supabase project and review pending migrations before applying them:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase migration list
supabase db push
```

Do not commit project credentials or database passwords. The project reference is not a secret, but database passwords and access tokens are.

## Admin authentication setup

Follow [Admin Authentication and RBAC](./admin-authentication.md) to:
- Disable public sign-ups.
- Provision the first owner using Supabase Auth and a trusted SQL insert.
- Provision additional roles until the owner-only invitation interface exists.
- Test login at `/admin/login`.

The application does not provide public admin registration. A Supabase Auth user without an active `admin_profiles` row is not an administrator.

## Security model

- Anonymous visitors can select active categories and active subcategories only.
- Active administrator profiles can read inactive catalog rows for management.
- Owner, admin, and catalog_manager can mutate catalog records through RLS.
- Viewer is read-only.
- Administrator profile writes have no browser-facing RLS policy. Account provisioning and role changes remain trusted operator operations until the owner-only management interface is implemented.
- Audit logs are readable only by owner and admin. Catalog insert/update/deactivate events are generated by database triggers; clients have no direct insert/update/delete policy.
- The last active owner cannot be demoted, deactivated, or deleted. The follow-up migration attaches and serializes this database guard.
- No password, game account credential, OTP, or service-role key is stored in these application tables.

## Important implementation boundary

The Proxy refreshes Supabase sessions; it is not the sole authorization boundary. Protected admin pages and future mutations must verify the authenticated claims and active `admin_profiles` role on the server. Database RLS remains the final data-access boundary.

Do not add Supabase service-role credentials to public variables or import a service-role client into Client Components. The storefront remains on its TypeScript catalog until a separate, parity-tested database cutover.
